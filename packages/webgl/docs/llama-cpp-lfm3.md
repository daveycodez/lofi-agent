## Tensors in the GGUF

ggml shapes are `[ne0, ne1]` with ne0 the contiguous (input-feature) dimension, so a
`[2048, 6144]` weight is the HF `[out=6144, in=2048]` matrix stored row by row. Quantized
blocks (32 for Q4_0, 256 for Q6_K) run along ne0, the input dimension.

| GGUF name | Type | ggml shape | HF name |
| --- | --- | --- | --- |
| `token_embd.weight` | Q6_K | [2048, 128000] | `model.embed_tokens.weight`, also the tied lm_head (no `output.weight` in the file; `lfm3.cpp:33-36`) |
| `output_norm.weight` | F32 | [2048] | `model.embedding_norm.weight` (it is the *final* norm despite the HF name) |
| `rope_freqs.weight` | F32 | [64] | generated by the converter: 32 × `1.0`, then 32 × `1e30` |
| `blk.N.attn_norm.weight` | F32 | [2048] | `operator_norm` |
| `blk.N.post_attention_norm.weight` | F32 | [2048] | `post_operator_norm` (all layers, conv too) |
| `blk.N.ffn_norm.weight` | F32 | [2048] | `ffn_norm` |
| `blk.N.post_ffw_norm.weight` | F32 | [2048] | `post_ffn_norm` |
| `blk.N.ffn_gate.weight` | Q4_0 | [2048, 7680] | `feed_forward.w1` |
| `blk.N.ffn_up.weight` | Q4_0 | [2048, 7680] | `feed_forward.w3` |
| `blk.N.ffn_down.weight` | Q4_0 | [7680, 2048] | `feed_forward.w2` |
| `blk.N.shortconv.in_proj.weight` | Q4_0 | [2048, 6144] | `conv.in_proj` |
| `blk.N.shortconv.conv.weight` | F32 | [7, 2048] | `conv.conv.weight` [2048, 1, 7] squeezed |
| `blk.N.shortconv.out_proj.weight` | Q4_0 | [2048, 2048] | `conv.out_proj` |
| `blk.N.attn_q.weight` | Q4_0 | [2048, 2048] | `self_attn.q_proj` |
| `blk.N.attn_k.weight` | Q4_0 | [2048, 512] | `self_attn.k_proj` |
| `blk.N.attn_v.weight` | Q4_0 | [2048, 512] | `self_attn.v_proj` |
| `blk.N.attn_q_norm.weight` | F32 | [128] | `self_attn.q_norm` |
| `blk.N.attn_k_norm.weight` | F32 | [128] | `self_attn.k_norm` |
| `blk.N.attn_gate.weight` | Q4_0 | [2048, 16] | `self_attn.gate_proj` |
| `blk.N.attn_output.weight` | Q4_0 | [2048, 2048] | `self_attn.o_proj` |

Conversion (`conversion/lfm3.py`):

- No q/k permutation. `LFM3Model` derives from `TextModel`, not the Llama converter that
  permutes q/k for interleaved RoPE, and llama.cpp runs NEOX RoPE, which is HF's
  `rotate_half` layout (`lfm3.py:13-55`).
- No norm offsets: every norm weight is used as `x_normed * w` (HF's `Lfm3RMSNorm` has no
  `1 + w` either).
- The conv weight is squeezed from [2048, 1, 7] to [2048, 7] (`lfm3.py:50-55`), which is
  ggml `[7, 2048]`: 7 taps contiguous per channel, tap 0 oldest, tap 6 the current token.
- `rope_freqs` is generated from `partial_rotary_factor` (`lfm3.py:37-48`):
  `rope_angles = int(0.5 * 128) // 2 = 32`, factors `[1.0]*32 + [1e30]*32`.
- Per-layer kv head counts are written with 0 for conv layers (`lfm3.py:22-26`).

## Whole model

`src/models/lfm3.cpp:90-197`. Names in quotes are the ggml tensor names the graph callback
gives (`cb(...)`). `llama_context::graph_get_cb` (`src/llama-context.cpp:2865-2871`) names a
tensor `"<name>-<il>"` with a plain `printf("%s-%d")`: the `{}` in names like
`model.layers.{}.operator_norm` is **not** substituted, so the layer-0 tensor is literally
`model.layers.{}.operator_norm-0`.

```
h = get_rows(token_embd, tokens)                       "model.embed_tokens"   (Q6_K → f32, no scaling)
for il in 0..23:
    x  = rms_norm(h) * attn_norm                         "norm-il", "model.layers.{}.operator_norm-il"
    o  = conv_block(x) if conv layer else attn_block(x)
    o  = rms_norm(o) * post_attention_norm               "model.layers.{}.post_operator_norm-il"
    h  = h + o                                           (unnamed ADD; "resid_mid" in the dumps)
    f  = rms_norm(h) * ffn_norm                          "model.layers.{}.ffn_norm-il"
    f  = ffn(f)
    f  = rms_norm(f) * post_ffw_norm                     "model.layers.{}.post_ffn_norm-il"
    h  = h + f                                           "l_out-il"
y = rms_norm(h) * output_norm                            "result_norm"
logits = token_embd · y                                  "result_output"  (tied Q6_K head)
```

- Lines: operator norm `lfm3.cpp:151-152`, post-operator norm `161-164`, residual `171`,
  FFN norm `173-174`, FFN `176`, post-FFN norm `178-181`, residual `183`, `l_out` `185-186`,
  final norm `189-190`, head `193-194`.
- No embedding scale (`build_inp_embd` default `tok_scale = 1.0f`, `llama-graph.h:1242`),
  no logit scale, no final-logit softcap: none of those ops is in the graph. **Verified**:
  `operator_norm-0 == rms_norm(inp_embd) * attn_norm`.
- For the last layer the graph keeps only the rows that produce output (`lfm3.cpp:166-169`);
  with every position requested as output this is the identity.
- `build_cvec` (`lfm3.cpp:185`) is a no-op without a control vector.
- The post norms are optional in the loader (`lfm3.cpp:45-50`) but present in this GGUF for
  every layer.

## Short-conv layer

`build_lfm_shortconv`, `src/models/lfm-base.cpp:9-85`. With `x` the operator-norm output
`[2048, T]`:

1. `bcx = in_proj · x` → `[6144, T]`, `"model.layers.{}.conv.in_proj-il"` (`lfm-base.cpp:28-29`).
2. Chunk along features, in this order (`lfm-base.cpp:31-39`), **verified**:
   - `B = bcx[0:2048]`
   - `C = bcx[2048:4096]`
   - `x = bcx[4096:6144]`

   Same order as HF's `B, C, x = BCx.chunk(3, dim=-2)`.
3. `bx = B * x` (elementwise), transposed to time-major per channel (`lfm-base.cpp:41`).
4. Prepend the conv state: `sx = concat(state, bx)` along time, `[6 + T, 2048]`
   (`lfm-base.cpp:43-50`). The state holds the previous **6** (`d_conv = l_cache - 1`) values
   of `B*x` per channel, not in_proj outputs. It is f32
   (`llama-model.cpp:3192-3193`, `n_embd_r = 2048*6`, `llama-hparams.cpp:214-216`). A fresh
   sequence starts from zeros: `build_rs` zeroes the cleared slot with
   `ggml_scale_inplace(.., 0)` (`llama-graph.cpp:3893-3912`).
5. Write back the new state: the last 6 columns of `sx` (`lfm-base.cpp:59-72`). Across
   ubatches this is exactly "keep the last 6 `B*x` values". (With `n_rs_seq > 0`, extra
   snapshots are written for rollback; they do not change the math.)
6. `conv = ggml_ssm_conv(sx, conv.weight)` → `[2048, T]`, `"model.layers.{}.conv.conv-il"`
   (`lfm-base.cpp:74-76`). CPU kernel, `ggml/src/ggml-cpu/ops.cpp:9907-9957`:

   ```
   conv[t, c] = Σ_{k=0..6} sx[t + k, c] * w[k, c]        (f32, summed k = 0 → 6 in order)
              = Σ_{k=0..6} bx[t - 6 + k, c] * w[k, c]    (bx[<0] = state, zeros at sequence start)
   ```

   Tap `w[6, c]` multiplies the current token and `w[0, c]` the token 6 steps back, as in
   HF's `Conv1d(padding=6)` truncated to the first T outputs. **Verified** (reversed taps give
   ~100% error).
7. `y = C * conv` (`lfm-base.cpp:78`), then `out_proj · y` → `"model.layers.{}.conv.out_proj-il"`
   (`lfm-base.cpp:79-80`).

No bias anywhere (`conv_bias: false` in HF; no bias tensors in the GGUF).

## Attention layer

`build_attn_block`, `src/models/lfm3.cpp:92-136`, then `build_attn` for the iSWA cache
(`src/llama-graph.cpp:3496-3589`) and `build_attn_mha` (`llama-graph.cpp:2963-3102`). Input
`x` is the operator-norm output `[2048, T]`.

1. Projections, separate q/k/v (`build_qkv`, `llama-graph.cpp:1818-1932`; no fused `wqkv`
   in this GGUF, no biases, no clamp):
   - `q = attn_q · x` → `[128, 16, T]`, `"Qcur-il"`
   - `k = attn_k · x` → `[128, 4, T]`, `"Kcur-il"`
   - `v = attn_v · x` → `[128, 4, T]`, `"Vcur-il"`

   Head `h` is features `h*128 .. h*128+127` of the projection output.
2. QK norm, per head over the 128 dims, **before** RoPE (`lfm3.cpp:108-111`):
   - `q = rms_norm(q) * attn_q_norm` → `"model.layers.{}.self_attn.q_layernorm-il"`
   - `k = rms_norm(k) * attn_k_norm` → `"model.layers.{}.self_attn.k_layernorm-il"`

   `v` is not normed. **Verified**.
3. RoPE, `ggml_rope_ext(.., n_dims = 128, mode = NEOX, ..)` on q and k (`lfm3.cpp:113-116`).
   - LFM3 is in the `LLAMA_ROPE_TYPE_NEOX` list (`llama-model.cpp:3642-3665`).
   - Frequency base: 1e6 in full layers (`cparams.rope_freq_base`, from `rope.freq_base`,
     `llama-context.cpp:226`) and 1e4 in sliding layers (`hparams.rope_freq_base_train_swa`,
     `llama-model.cpp:2778-2780`).
   - `freq_scale = 1`, `ext_factor = 0` (no YaRN, `llama-context.cpp:265-266`),
     `attn_factor = 1`.
   - Freq factors: `rope_freqs` in full layers, none (nullptr) in sliding layers
     (`lfm3.cpp:104`).

   CPU kernel, `ops.cpp:6172-6186` (cache) and `6260-6277` (rotation), for position `p`:

   ```
   theta_scale = powf(base, -2/128)                      (ops.cpp:6340)
   theta_i     = p * theta_scale^i / ff[i],  i = 0..63    (computed as theta *= theta_scale in f32)
   for i in 0..63:   (NEOX pairs element i with element i + 64)
       x0 = v[i]; x1 = v[i + 64]
       out[i]      = x0*cos(theta_i) - x1*sin(theta_i)
       out[i + 64] = x0*sin(theta_i) + x1*cos(theta_i)
   ```

   - Full layers: `ff[i] = 1` for i < 32 and `1e30` for i ≥ 32, so pairs 32..63 get an angle
     of about `p * 1e-30`, effectively 0 (cos = 1, sin ≈ 1e-30·p). Rotated dims are 0..31 and
     64..95; dims 32..63 and 96..127 pass through unchanged (measured difference ≤ 1e-31).
     The 32 live frequencies are `1e6^(-2i/128)`, i = 0..31: the first 32 of the
     **full-head** progression, not `1e6^(-2i/64)`.
   - Sliding layers: all 64 pairs rotate, `theta_i = p * 1e4^(-2i/128)`.

   **Verified**: NEOX matches to 1e-5 relative; interleaved (NORM-mode) pairing gives 170%
   error.
4. KV cache store (`llama-graph.cpp:3552-3561`): k after RoPE and v (not normed) are written
   into the layer's cache, **f16** by default (`type_k = type_v = F16`). Full layers use the
   base cache and sliding layers the SWA cache. With flash attention the V cache is not
   transposed. There is no Hadamard rotation: it is only enabled for quantized KV types
   (`llama-kv-cache.cpp:310-327`).
5. Attention, `scale = 1/sqrt(128)` (`lfm3.cpp:118-120`), no softcap
   (`attn_soft_cap` unset), no ALiBi, no sinks, no KQ bias.
   - Mask (`llama-kv-cache.cpp:1545-1690`): key at position `pj` is visible to the query at
     `pq` iff it belongs to the same sequence and
     - causal: `pj <= pq` (masked if `p0 > p1`, `:1656`)
     - sliding layers only: `pq - pj < 256` (masked if `p1 - p0 >= n_swa`,
       `llama-hparams.h:526-531`).

     A sliding query sees 256 keys, itself and the 255 before it. **Verified**: the dumped
     layer-4 output matches `< 256` to 6e-7 relative at positions ≥ 256; `< 257` or `< 255`
     give 3% and 7% error. This equals HF's `kv_idx > q_idx - sliding_window`. Masked
     entries are `-INFINITY` (f16 mask when flash attention is on, `llama-graph.cpp:30-47`).
   - GQA: query head `h` reads kv head `h / 4` (integer division; heads 0-3 → kv 0,
     4-7 → kv 1, ...). In the CPU FA kernel this is `ik2 = iq2 / rk2` with
     `rk2 = n_head / n_head_kv` (`ops.cpp:8866, 8929`). Same as HF's `repeat_kv`. **Verified**.
   - Output: `softmax(q·kᵀ·scale + mask) · v` per head, reshaped to `[2048, T]` with feature
     `h*128 + d`: `"kqv_out-il"`, renamed `"attn_out-il"` (`llama-graph.cpp:3570`,
     `lfm3.cpp:121`).
6. Output gate (`lfm3.cpp:123-130`):
   - `g = sigmoid(attn_gate · x)` → `[16, T]`, `"model.layers.{}.self_attn.gate-il"`
     (stored after the sigmoid). Its input is `x`, the **operator-norm output** (the
     attention block's input), as in HF (`gate_proj(hidden_states)`).
   - `attn_out[h*128 + d, t] *= g[h, t]`: one scalar per head and token.

   **Verified**.
7. `attn_output · gated` → `"model.layers.{}.self_attn.out_proj-il"` (`lfm3.cpp:132-133`),
   then the post-operator norm.

Flash attention: `flash_attn_type` defaults to AUTO, and AUTO resolves to on for the CPU
backend (`llama-context.cpp:322-323, 660-662`); the dumped graph has `FLASH_ATTN_EXT`.
wllama does not override it. Without FA the math is the same up to rounding (`mul_mat` k·q
in f32, `soft_max_ext` with the same scale and mask, `llama-graph.cpp:3034-3088`).

## FFN

`build_lfm_dense_ffn` → `build_ffn(.., LLM_FFN_SILU, LLM_FFN_PAR)` (`lfm-base.cpp:87-98`,
`llama-graph.cpp:1933-2140`):

- `gate = ffn_gate · f` → `"ffn_gate-il"` [7680, T]
- `up = ffn_up · f` → `"ffn_up-il"`
- `s = silu(gate) * up` (fused `ggml_swiglu_split`, `llama-graph.cpp:2036`) → `"ffn_swiglu-il"`
- `out = ffn_down · s` (unnamed MUL_MAT; `"ffn_out"` in the dumps)

`silu(x) = x / (1 + exp(-x))`. On the CPU, NEON uses a polynomial `expf` (`ggml_v_silu`,
`ggml/src/ggml-cpu/vec.h:1154-1180`); the scalar tail and WASM use libm `expf`
(`vec.cpp:458-460`). `swiglu_clamp_shexp` is 0 for LFM3, so there is no clamp.

## RMSNorm

`ggml_rms_norm` with eps 1e-5 (`build_norm`, `llama-graph.cpp:1768-1802`). CPU kernel
`ops.cpp:4070-4130`:

```
sum   = Σ x_i²            (accumulated in double, ggml_float)
mean  = (float)(sum / n)
scale = 1.0f / sqrtf(mean + eps)
y_i   = x_i * scale * w_i      (the backend may fuse RMS_NORM and MUL; same result)
```

The same op is used for operator/post/ffn/final norms (n = 2048) and the per-head QK norms
(n = 128). `build_norm` names the un-weighted result `"norm-il"`, which is why many tensors
are called `norm-il`.

## Precision on the CPU backend

wllama's WASM build runs the same kernels, with scalar or WASM SIMD code instead of NEON.
Accumulation order differs, and so does the Q8_0 rounding (next point).

- **Q4_0 matmuls quantize the activations to Q8_0.** `vec_dot_type` of Q4_0 is Q8_0
  (`ggml/src/ggml-cpu/ggml-cpu.c:240-243`). Each 32-element block of the f32 activation row
  is quantized with:

  ```
  amax = max|x_j|; d = amax/127; id = d ? 1/d : 0
  q_j  = round(x_j * id)         (NEON: vcvtnq, round-half-even; scalar _ref: roundf)
  stored d = fp16(d)
  ```

  (`ggml-cpu/arch/arm/quants.c:41-83`). The dot product is
  `Σ_blocks fp32(d_w) * fp32(d_x) * Σ_j (qw_j - 8) * q_j`, with integer inner sums.
  - **The browser's wllama truncates instead of rounding.** The WASM SIMD quantizer that the
    browser builds select (`-DEMSCRIPTEN_SYSTEM_PROCESSOR=wasm`, `__wasm_simd128__`) does
    `q_j = wasm_i32x4_trunc_sat_f32x4(x_j * id)`, which truncates toward zero
    (`ggml-cpu/arch/wasm/quants.c:71-74`). Its Q8_K quantizer rounds first
    (`wasm_f32x4_nearest`, `:191-199`); only Q8_0 truncates. None of the repo's patches
    change this.
  - Emulated natively, by building with `vcvtq_s32_f32` (truncate) instead of
    `vcvtnq_s32_f32`: see `logits_q8trunc.bin` below. This moves the logits about twice as
    far from the rounding build as Metal does.
  - The reference tensors use native rounding. An engine that rounds will match them
    better than it matches the browser's wllama.
  - **Verified**: `ffn_down` output matches the Q8_0-activation emulation to 4.5e-6
    relative, against 6.8e-4 with f32 activations.
  - This requantization makes the network chaotic at the 1e-3 level: a 1e-6 change in an
    input can flip an int8 rounding (see [Noise floor](#noise-floor-cpu-against-metal)).
- **The Q6_K lm_head quantizes the activations to Q8_K**: 256-element blocks, f32 scale
  `d = 1/iscale` with `iscale = -127/x[argmax|x|]`, `q = nearest_int(iscale*x)` clamped to
  127 (`ggml-cpu.c:327-330`, `ggml-quants.c` `quantize_row_q8_K_ref`). **Verified**: 9.5e-8
  relative, against 6.2e-3 with f32 activations.
- Embedding lookup: Q6_K rows dequantized to f32 (`GET_ROWS`).
- KV cache: K (after RoPE) and V rounded f32 → f16 when stored.
- Flash attention on the CPU (`ops.cpp:9416-9550`):
  - Prompt / batch path, 64 or more query rows (`use_tiled`, `ops.cpp:9521-9545`,
    `GGML_FA_TILE_Q = 64`): Q stays f32, K/V tiles are converted f16 → f32, f32 GEMMs, f32
    online softmax and accumulator (`ops.cpp:9056-9345`).
  - Fewer than 64 query rows, which includes single-token decode
    (`ggml_compute_forward_flash_attn_ext_f16_one_chunk`, `ops.cpp:8818-9055`): Q is
    converted to **f16**, `q·k` uses `ggml_vec_dot_f16`, and for an f16 V cache the weighted
    sum of V is **accumulated in f16** (`VKQ16`, `ops.cpp:8919, 8968-8982`), converted to
    f32 at the end. The decode path is less precise than the prompt path.
  - Decode with at least 512 cached keys and a single query uses a split-KV variant of the
    same one_chunk kernel (`ops.cpp:9465-9497`).
- Conv state: f32. Conv: f32 sum of 7 products (not `ggml_vec_dot_f32`, which would sum in
  double).
- Sigmoid: `1/(1+expf(-x))` in f32 (`vec.h:935`).
- RoPE: f32; angles by repeated f32 multiplication, `cosf`/`sinf`.
- KV cache type default f16 (`llama_context_default_params`, `type_k/type_v`); wllama only
  overrides it if `cache_type_k/v` are passed, and the app does not.

For comparison, the Metal backend (full offload) does **not** quantize activations: its
mat-mat kernels round the activations to f16 and multiply by dequantized weights with f32
accumulation (**verified**: Metal's `in_proj` output matches `f16(x)·W` to 1e-6 relative,
against 4.6e-5 for `f32(x)·W`). A WebGL engine that multiplies f16/f32 activations by
dequantized Q4_0 weights will behave like Metal, not like the CPU backend; to track wllama
more closely it would have to quantize activations to Q8_0 per 32 (and Q8_K per 256 for the
head).

App context (wllama, `packages/wllama/src/client.ts:225-238`): `n_gpu_layers: 0`,
`swa_full: true`, flash attention AUTO (on), KV f16, `n_ubatch` default 512, unified KV with
`n_parallel` 4. `swa_full` only changes the SWA cache size (`llama-kv-cache-iswa.cpp:73-80`);
the mask makes the result identical.

## Differences from the HF code and from the original summary

The original summary is correct on every point it makes. Details to be precise about:

1. **Partial RoPE frequencies.** The 32 live frequencies are `1e6^(-2i/128)`, i = 0..31,
   the first half of the full-head progression (HF `compute_default_rope_parameters` does
   the same: `arange(0, 64, 2) / 128`). NEOX pairs `(i, i+64)`, so dims 0-31 and 64-95
   rotate, and dims 32-63 and 96-127 are unchanged.
   - llama.cpp gets there with `n_rot = 128` and freq factors of `1e30` (an angle of
     ~1e-30·p rather than exactly 0).
   - HF uses inverse frequencies of exactly 0. The two are equal in f32.
2. **Sliding layers rotate all 128 dims** with base 1e4 and no freq factors. There is no
   partial rotation there; the `rope_freqs` tensor is only applied in full-attention layers.
3. **The gate's input** is the operator-norm output `x`, the same input as q/k/v, not the
   attention output. It is applied as one scalar per head to the attention output before
   `o_proj` (`attn_gate.weight` is Q4_0 too).
4. **Sliding window boundary**: key visible iff `0 <= pos_q - pos_k < 256` (256 keys
   including the query itself). HF's `sliding_window_overlay` is the same.
5. **Conv state** keeps the previous 6 values of `B*x`, not 7, and not the in_proj output.
6. **No q/k permutation, no norm offsets, no embedding scale, no logit scale or softcap.**
7. HF's `embedding_norm` is the *final* norm (GGUF `output_norm`); nothing normalizes the
   embeddings.
8. Numerical differences only:
   - HF runs RMSNorm with the weight multiply in the model dtype (bf16) and RoPE in f32
     from `base ** (arange/dim)`.
   - llama.cpp is f32 throughout, except for the Q8_0/Q8_K activation quantization and the
     f16 KV cache above, and builds RoPE angles by repeated f32 multiplication.
9. The chat template ends the generation prompt with `<think>` when thinking is on (HF
   default) and with `<think></think>` when it is off. The reference prompt uses thinking
   off.
10. **Native llama.cpp and the browser's wllama differ in Q8_0 rounding.** On the CPU
    backend, activations are quantized to Q8_0 before every Q4_0 matmul. Native builds round
    to nearest; the WASM SIMD build truncates toward zero. See
    [Precision](#precision-on-the-cpu-backend).

## Reference tensors

Produced by a small tool against libllama (eval callback plus `llama_get_logits_ith`):
- Output: one float32 file per tensor, row-major [token][feature], listed in a `manifest.json`
  with each file's shape and the ggml tensor it came from (`bench/README.md` says how
  the check page reads them).

Build and run settings:
- CPU build: `GGML_METAL=OFF GGML_BLAS=OFF GGML_ACCELERATE=OFF GGML_CPU_REPACK=OFF`,
  native NEON + dotprod + i8mm. BLAS/Accelerate is off because it would dequantize Q4_0 to
  f32 for large batches, and repack is off to stay on the generic Q4_0·Q8_0 path.
- Run: `n_gpu_layers = 0`, 16 threads, `swa_full = true`, flash attention AUTO (on), KV
  f16, all positions output.
- Metal: the same source with `GGML_METAL=ON`, `n_gpu_layers = 99`.

Prompt: system and user messages rendered with the GGUF's chat template by llama.cpp's
jinja renderer (`enable_thinking = false`, generation prompt on), then tokenized with
special-token parsing and no extra BOS: **345 tokens**, positions 0..344.

Files (all raw little-endian, no header; full list with shapes and ggml names in
`manifest.json`):

- `tokens.json`: prompt text, messages, token ids and pieces, greedy continuations
  (CPU and Metal). `tokens.bin`: the ids as int32.

## Noise floor: CPU against Metal

Two correct implementations of this graph differ by this much, measured against
`logits.bin`:

| Run | max abs, all logits | mean abs | per-position max abs: median / p90 / p99 / max | top-1 agreement | ref top-1 in other's top-5 | KL(ref‖other): mean / max |
| --- | --- | --- | --- | --- | --- | --- |
| Metal, one decode | 1.27 | 0.048 | 0.28 / 0.55 / 0.96 / 1.27 | 333 / 345 | 345 / 345 | 3.0e-3 / 8.2e-2 |
| CPU, batches of 128 | 1.75 | 0.057 | 0.34 / 0.61 / 1.07 / 1.75 | 335 / 345 | 345 / 345 | 4.4e-3 / 1.8e-1 |
| CPU, Q8_0 truncated as in the browser's WASM build (emulated) | 3.89 | 0.115 | 0.67 / 1.35 / 2.60 / 3.89 | 318 / 345 | 344 / 345 | 2.0e-2 / 5.7e-1 |

Logits are about 10-20 for the top token. In the Metal and batch-128 runs, every top-1
disagreement happens where the reference's top-2 margin is small (0.004-0.94; a margin of
0.94 once, otherwise below 0.7). The truncating build's 27 disagreements all have margins
below 0.69.

- **Batching changes CPU results as much as switching to Metal.** Position 0 already differs
  by 0.11 between batch 345 and batch 128.
  - The matmul kernels tile differently by batch size, which changes `in_proj` by about
    1e-6 relative.
  - Q8_0 requantization in the next matmul turns that into about 2e-3 (`ffn_gate-0`).
  - From there the differences grow through the layers.
- Greedy decoding agrees for the first 16 tokens between CPU and Metal, and also between
  CPU and the truncating build. After that the runs diverge into different but equally
  plausible text.
- CPU against Metal, intermediates (`rms(diff)/rms(ref)`, worst-token cosine):
  - layer 0: 3-9e-3, cos ≥ 0.99985
  - layers 2 and 4: 0.8-1.9e-2, cos ≥ 0.9994
  - `l_out-23`: 3.6e-2, cos 0.9947
  - `result_norm`: 3.6e-2, cos 0.9945

  Per tensor in `noise_floor.json`.

Suggested tolerances for the WebGL engine against `logits.bin`, from the Metal and batch
rows (to compare against the browser's wllama instead, use the looser truncation row):
- per-position max abs logit difference around 0.3 median and ≤ 1.5-2 worst case
- mean abs around 0.05
- top-1 agreement ≥ 95%, with every disagreement at a small reference margin
- reference top-1 always in the engine's top-5

Anything well beyond these (for example a systematic error at positions ≥ 256 in sliding
layers, or in full layers' dims 32-63) is a bug, not noise.
